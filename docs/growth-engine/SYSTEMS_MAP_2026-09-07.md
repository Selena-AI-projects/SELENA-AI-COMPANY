## 2. Люди и доступ

### Кабинет (`staging-cabinet.`)

- Режим `DEPLOYMENT_MODE=local`: ровно **один** аккаунт. Второй sign-up код
  отвергает («already bootstrapped»). Сейчас это ваш аккаунт; организация
  «Selena Systems» (флаг `SELENA_STAGING_MVP`), бренды `selena` (засеян) и
  `other bali` (создан вами через онбординг).
- Приглашения команды (`teamInvites`) существуют в коде только для режима
  `cloud`. В `local` их нет — это не переменная, а код: защита второго sign-up,
  флаг режима и отправка писем (Resend) живут в разных пакетах.
- Роли внутри Content OS, когда аккаунтов станет больше: `owner` (admin/owner
  организации) — всё, включая одобрение, релизы, kill switch, политику контента,
  подтверждение источника; `member` — создаёт черновики и версии, **не
  одобряет**; `viewer` — только чтение; `api_key` — пишет с правом
  `client:write`, **никогда не одобряет**. Одобрение возможно только из живой
  сессии владельца — это закреплено и в коде, и в базе (`can_human_approve`).
- Синтетический владелец приёмки (`growth-check-org`, GD-11) остаётся в базе
  строкой — ничего не одобрял, ни на что не влияет.
- Вход через Google на staging возможен только под флагами
  `SELENA_STAGING_GOOGLE_SIGN_IN_ENABLED` + `SELENA_STAGING_MVP`; значение флага
  не читалось.

### AI Visibility (`app.`)

- Тоже `local`-режим (в форке облачный режим запрещён), но у форка **свой**
  механизм: allowlist приглашений + лимит мест + Google OAuth. Значения флагов
  `SELENA_SELF_SERVE_SIGNUP…`, `SELENA_PAYMENTS_ENABLED` не читались; список
  аккаунтов не перечислялся (базы этого проекта в аудит не входили).
- Аудит платформы в самом репозитории: 62/100, NO-GO на production; блокер —
  auth-wall Perplexity у Bright Data. К кабинету по замыслу отношения не имеет.

### Aether (`os.` / `studio.`)

- Аутентификация Supabase Auth, email + пароль. Роли `admin | editor | viewer`,
  источник истины — `profiles.role`, читается на каждый запрос; новый
  пользователь по умолчанию `viewer` (не может тратить бюджет).
- Самостоятельной регистрации нет: **admin заводит сотрудника в UI** (email,
  пароль ≥ 8, роль) через Supabase Admin API; первый admin ставится вручную в
  Supabase. Кто заведён сегодня — не перечислялось (личные данные).
- `admin`: команда, реестр агентов, skill packs, интеграции, диагностика.
  `editor`: задачи, проекты, файлы. `viewer`: чтение.

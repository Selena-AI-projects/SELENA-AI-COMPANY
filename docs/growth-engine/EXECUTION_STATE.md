### Блокировка: доступ к GitHub пропал

2026-09-07 ~02:15 UTC доступ сессии к GitHub перестал работать: `git push` и
`git fetch` отвечают **403**, GitHub API — **404** на все репозитории проекта,
включая `selena-ai-visibility`. При этом сессия аутентифицирована как
`parkourcafe`, а список разрешённых репозиториев не менялся. Значит, отозван или
сузился грант GitHub-приложения, а не права сессии.

Railway собирает образы только из GitHub по SHA, локальную загрузку исходников
не принимает, а сам staging из этого контейнера недоступен по сети. Поэтому
следующий прогон невозможен, пока доступ не восстановлен.

Готовые, но **не отправленные** коммиты (`integration/content-os-growth-ge5`,
локально): `21c7873e`, `0277f256`, `a6f7ccf3`. Последний отправленный SHA —
`78e46937`.

Разрешилось 2026-09-07 02:27 UTC: репозитории переехали в организацию
**`Selena-AI-projects`** (`Selena-AI-projects/selena-OS`,
`…/SELENA-AI-COMPANY`, `…/Aether-Medium`), приложение Claude получило к ним
доступ, все коммиты отправлены (`integration/content-os-growth-ge5` @ `a6f7ccf3`).

Осталась вторая половина того же переезда — **Railway**. Все сервисы staging
привязаны к старому пути `parkourcafe/selena-OS`; деплой по SHA отвечает
`No GitHub installation found for repo: parkourcafe/selena-OS`, а перепривязка
на `Selena-AI-projects/selena-OS` — `User does not have access to the repo`.
Значит, GitHub-приложение Railway не установлено на организацию
`Selena-AI-projects`. Это действие владельца в GitHub/Railway; из сессии оно
недоступно. Пока оно не сделано, ни один сервис staging (`web`, `receiver`,
`projection`, `migrate`, временные) пересобрать нельзя — работающие деплои при
этом продолжают работать.

### Установленный факт: staging принимает ровно один аккаунт

Прогон `d7ec4cce` (режим `accounts`) прочитал состояние: **1 пользователь**
(создан 2026-09-05T00:46 UTC), 1 credential-аккаунт, 1 организация. Регистрация
второго аккаунта отвечает `422 FAILED_TO_CREATE_USER` — это хук local-режима
`user.create.before`, который отклоняет любую регистрацию после первой.

Решение (GD-11): проверка заводит **собственную** учётную запись строкой в базе,
пароль хешируется тем же пакетом `@better-auth/utils@0.4.2`, которым приложение
пароли и проверяет. Вход выполняется штатным `/api/auth/sign-in/email`, всё
проверяемое — бренд, политика, подтверждение источника — идёт через интерфейс.
Аккаунт владельца не используется, сессия не подделывается. Ограничение честное
и попадёт в итоговый отчёт: обойдён продуктовый лимит «один аккаунт на local-
установку», потому что иначе отдельного синтетического владельца на этом стенде
не существует.

### Состояние базы изменилось после этого чтения

Слепок из §1.2 показал журнал уже на 38 записей вместо 37. Причина найдена по журналу
деплоев, а не додумана: 2026-09-06T03:01:07 UTC сервис `migrate` задеплоил коммит
`313daa0c5` («Merge pull request #28 … Content OS Slice 1»), деплой `fc03b98c-…`, SUCCESS.
Команда запуска сервиса к тому моменту была возвращена с инспектора на
`node scripts/run-migrations.mjs`. Хеш новой записи журнала —
`bd0e108b…310d7` — совпадает с файлом `0037_content_project_profiles.sql` побайтно.

Значит **`0037` применена на staging другим исполнителем**, и таблица §2 читается так: журнал
38 записей, `0037` применена, `0038`/`0039` — нет.

Отсюда же следствие, которое важнее самого факта: у сервиса `migrate` включён автодеплой с

исполнитель миграций» не обеспечивается ничем: любой следующий push в эту ветку применит
миграции сам, без меня и без вашего решения.

Сервис `migrate` оставлен с командой инспектора. Это и есть безопасное состояние: если на
ветку, с которой он собирается, что-то прилетит, автодеплой запустит чтение, а не миграции.
Команду миграций я поставлю отдельным осознанным шагом, когда условия ниже будут закрыты.

## 3. Порядок миграций — исправлено под фактический порядок и доказано

Найдено при проверке обеих последовательностей, как вы и просили.

Drizzle применяет миграцию только если её отметка времени больше самой поздней записанной, и
**молчит о пропущенных**: прогон печатает «migrations applied successfully», а схема остаётся
без них. Проверено на одноразовых базах настоящими файлами обеих веток, в обе стороны:

| Что применено первым | Затем | Итог |
|---|---|---|
| `0037` | growth с отметками ниже | growth рапортует успех, `0038`/`0039` не применены |
| growth с отметками выше `0037` | мигратор второй ветки | он рапортует успех, **`0037` не применена**, её объектов нет |

Ловушка симметрична: проигрывает тот, кто приходит вторым.

**Структурная защита.** В общий `run-migrations.mjs` добавлена проверка: если ожидающая
миграция была бы пропущена, раннер **останавливается с объяснением** вместо рапорта об успехе.
Раннер общий, поэтому после слияния защита работает для обеих веток.

**Порядок.** Пока это готовилось, `0037` применилась на staging первой (§2). Вы выбрали
проверенный порядок: Growth `0038`/`0039` после неё. Отметки подняты выше `0037`:
`1788620400000` и `1788620460000` (коммит `cb11f0b`). Ни одна применённая миграция не
переписана — менялись только отметки ещё не применённых.

Проверено не на чистой базе, а на **копии текущего состояния staging**: миграции `0000`–`0036`
плюс `0037` из файла второй ветки и её запись в журнале с той же отметкой и тем же хешем, что
на staging.

| Проверка | Результат |

## 4. Совместимость receiver — проверена до редеплоя

Действующий отправитель — production Aether, пилот `other_bali`, контракт v1, старый секрет.
Проверялось не рассуждением, а исполнением: конверты собирал и подписывал **собственный
код Aether**, а разбирал — код обоих receiver.

| | receiver, развёрнутый сейчас (`05599f9`) | receiver этого среза |
|---|---|---|
| Событие v1 `task.result.ready` | принимает | принимает |
| Событие 1.1 `content.draft_ready` | **отвергает** (`unknown envelope schema version`) | принимает |

Живые ответы нового receiver на события production-отправителя, подписанные **старым**
секретом: `202 recorded`, повтор → `202 duplicate`, следующая версия → `202 recorded`,
старая версия после новой → `202 duplicate`. Тот же отправитель с новым секретом — тоже
принят (список секретов работает). Секрет, убранный из списка, → `401`.

Отсюда два следствия: обновление receiver **не** затрагивает действующего отправителя, и
receiver обязан быть обновлён **до** первой отправки 1.1 локальным producer.

Единственное изменение поведения для v1: та же версия того же агрегата с другим содержимым
теперь `409` вместо прежнего ответа. Production-отправитель этого не производит — у его
outbox есть уникальность `(destination, aggregate_id, version)`, а повтор шлёт то же тело.

## 7. Producer — одна команда и проверка готовности машины

Чтобы локальный запуск не превращался в развёртывание всего приложения, добавлена команда
`backend/scripts/run_growth_fixture_once.py`: она создаёт синтетический проект и задачу,
пишет файлы фикстуры, пропускает их через обычный outbox и доставляет на указанный receiver.
Веб-сервер не поднимается, модель не вызывается.

Проверено локально целиком: 3 события поставлены, 3 доставлены, приняты (`1 task.result.ready`,
`1.1 content.draft_ready` ×2), расход `tokens_in=0 tokens_out=0 cost=0.000000`.

**Ваша машина не считается подготовленной.** Поэтому рядом есть
`backend/scripts/check_growth_fixture_ready.py` — он ничего не меняет, только читает, и
останавливается на первой недостающей предпосылке, называя её и что с ней делать:

| Проверка | Что делает |
|---|---|
| интерпретатор | Python 3.11+, иначе называет найденную версию |
| файл окружения | есть ли `backend/.env`, и сколько переменных из него взято |
| зависимости | импортируются ли `asyncpg`, `httpx`, `pydantic`, `pydantic-settings`, `cryptography`; иначе — команда установки |
| настройки | та же проверка, что делает сам запуск, — не разъедутся |
| база | одно подключение и одно чтение; при отказе печатается **класс** ошибки, не адрес |
| миграции | все 23 миграции Aether на месте; иначе — первая недостающая по имени |
| receiver | отвечает ли что-нибудь по адресу; ничего не отправляется и не подписывается |

Все семь ветвей отказа проверены запуском, не рассуждением: старый интерпретатор,
отсутствующий `.env`, интерпретатор без зависимостей, выключенная фикстура, поднятый и
непод­нятый Postgres, пустая база, недоступный адрес.

**Исправлено попутно и важно для вас:** половина настроек читалась через
`pydantic-settings` (он сам открывает `.env`), половина — через `os.getenv` (он `.env` не
видит). Файл, в котором прописано всё, настраивал доставку и оставлял выключатели невидимыми.
Теперь оба скрипта кладут файл в окружение перед чтением, причём уже экспортированное значение
имеет приоритет над файлом.

```
# backend/.env — значения секретов вписываются на месте, не пересылаются
DATABASE_URL=postgresql://…            # локальная база Aether
SETTINGS_ENCRYPTION_KEY=…              # любой случайный ключ для локального запуска
CONTROL_ROOM_BRIDGE_ENABLED=true
CONTROL_ROOM_BRIDGE_BUSINESS_KEYS=selena
CONTROL_ROOM_BRIDGE_URL=https://receiver-production-3704.up.railway.app/v1/bridge/aether
CONTROL_ROOM_BRIDGE_SECRET=<новый секрет, скопированный из Railway>
AETHER_GROWTH_FIXTURE_ENABLED=true

# сначала — проверка готовности, она ничего не меняет
cd backend && python scripts/check_growth_fixture_ready.py
# и только если она сказала «Ready»
python scripts/run_growth_fixture_once.py
```

Шаблон этих переменных лежит в `backend/.env.example`, чтобы не сверяться с документом.

**Порядок подтверждения источника.** Проект не существует до запуска, поэтому подтверждать
нечего заранее. Запуск печатает `project: <uuid>` до доставки — этот uuid вы и подтверждаете в
Control Room → Sources для окружения staging. События, пришедшие до подтверждения, receiver не
теряет: они откладываются с причиной `NO_BINDING` и проецируются при следующей попытке worker
(30 с с удвоением до часа). Повторно запускать producer не нужно — повторный запуск создал бы
новую задачу и новые карточки.

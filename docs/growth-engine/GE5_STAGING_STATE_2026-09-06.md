восстановление в отдельный сервис — это новая база. Решение за вами (§5).

## 3. Порядок миграций — исправлено и доказано

Найдено при проверке обеих последовательностей, как вы и просили.

Drizzle применяет миграцию только если её отметка времени больше самой поздней записанной, и
**молчит о пропущенных**: прогон печатает «migrations applied successfully», а схема остаётся
без них. Проверено на одноразовых базах настоящими файлами обеих веток:

| Что применено первым | Затем | Итог |
|---|---|---|
| `0037` | growth с отметками ниже | growth рапортует успех, `0038`/`0039` не применены |
| growth с отметками выше `0037` | мигратор второй ветки | он рапортует успех, **`0037` не применена**, её объектов нет |

То есть прежнее решение (поднять наши отметки выше `0037`) создавало ровно ту проблему,
которую вы запретили: будущая `0037` молча пропускалась бы.

**Сделано:**

1. Отметки `0038`/`0039` возвращены **ниже** `0037`. Это порядок, который не требует от второй
   ветки ничего: после наших миграций её `0037` новее и применяется штатно. Проверено —
   после growth мигратор второй ветки применяет `0037`, объекты обеих веток на месте.
2. В общий `run-migrations.mjs` добавлена проверка: если ожидающая миграция была бы пропущена,
   раннер **останавливается с объяснением** вместо рапорта об успехе. Раннер общий, поэтому
   после слияния защита работает для обеих веток. Проверено: чистая база — без ложных
   срабатываний; неверный порядок — отказ, журнал не тронут; верный — применяется.
3. Открыт [issue #29](https://github.com/parkourcafe/selena-OS/issues/29) со всеми числами,
   требованием одного порядка и одного исполнителя миграций.

Инспектор подтвердил, что на staging сейчас именно тот порядок, который нужен: последняя
запись — `0036` (1787811060000), наши `0038`/`0039` (…120000 / …180000) новее и применятся,
а `0037` (1788620325000) новее их и применится после.

## 4. Совместимость receiver — проверена до редеплоя

Действующий отправитель — production Aether, пилот `other_bali`, контракт v1, старый секрет.
Проверялось не рассуждением, а исполнением: конверты собирал и подписывал **собственный
код Aether**, а разбирал — код обоих receiver.

| | receiver, развёрнутый сейчас (`05599f9`) | receiver этого среза |
|---|---|---|
| Событие v1 `task.result.ready` | принимает | принимает |
| Событие 1.1 `content.draft_ready` | **отвергает** (`unknown envelope schema version`) | принимает |

Живые ответы нового receiver на события production-отправителя, подписанные **старым**
секретом: `202 recorded`, повтор → `202 duplicate`, следующая версия → `202 recorded`,
старая версия после новой → `202 duplicate`. Тот же отправитель с новым секретом — тоже
принят (список секретов работает). Секрет, убранный из списка, → `401`.

Отсюда два следствия: обновление receiver **не** затрагивает действующего отправителя, и
receiver обязан быть обновлён **до** первой отправки 1.1 локальным producer.

Единственное изменение поведения для v1: та же версия того же агрегата с другим содержимым
теперь `409` вместо прежнего ответа. Production-отправитель этого не производит — у его
outbox есть уникальность `(destination, aggregate_id, version)`, а повтор шлёт то же тело.

проверил только его длину и класс символов, чтобы убедиться, что шаблон раскрылся.

**О бюджете честно:** Railway не даёт отдельного потолка расходов на сервис. Ограничение
уровня workspace я не трогал. Так что 10 $/мес — это оценка расхода одного маленького
сервиса без трафика, а не гарантированный платформой предел. Сервис можно остановить в любой
момент; пока флаг выключен, он не работает и после старта сразу завершается.

## 6. Бренд и политика контента — O18 подтверждённо открыт

Проверено по коду: **ни один путь UI или API не создаёт `selena_registry.content_policies`.**
Единственная вставка во всём репозитории — в тесте. Инспектор показал на staging 0 политик.

Значит политику придётся создать вручную под сессией владельца — и это **подготовка теста
транспорта, а не приёмка пользовательского пути**. O18 остаётся открытым. Бренд на staging
уже есть (1 запись); платный онбординг не понадобится.

Owner-only подтверждение источника и изоляция не ослабляются: подтверждение по-прежнему
проходит через `confirm_growth_binding` под сессией владельца, а серверные функции закрыты
флагом `GROWTH_ENGINE_STAGE1_ENABLED`.

## 7. Producer — одна команда, проверена

Чтобы локальный запуск не превращался в развёртывание всего приложения, добавлена команда
`backend/scripts/run_growth_fixture_once.py`: она создаёт синтетический проект и задачу,
пишет файлы фикстуры, пропускает их через обычный outbox и доставляет на указанный receiver.
Веб-сервер не поднимается, модель не вызывается.

Проверено локально целиком: 3 события поставлены, 3 доставлены, приняты (`1 task.result.ready`,
`1.1 content.draft_ready` ×2), расход `tokens_in=0 tokens_out=0 cost=0.000000`.

Что нужно на машине владельца: Python 3.11 с зависимостями `backend`, локальный Postgres с
применёнными миграциями Aether, ветка `growth/ge1-4-local-slice`.

```
# backend/.env — значения секретов вписываются на месте, не пересылаются
DATABASE_URL=postgresql://…            # локальная база Aether
SETTINGS_ENCRYPTION_KEY=…              # любой случайный ключ для локального запуска
CONTROL_ROOM_BRIDGE_ENABLED=true
CONTROL_ROOM_BRIDGE_BUSINESS_KEYS=selena
CONTROL_ROOM_BRIDGE_URL=https://<домен staging receiver>/v1/bridge/aether
CONTROL_ROOM_BRIDGE_SECRET=<новый секрет, скопированный из Railway>
AETHER_GROWTH_FIXTURE_ENABLED=true

# одна команда
cd backend && python scripts/run_growth_fixture_once.py
```

Команда сама откажется стартовать, если фикстура или мост не включены явно, если адрес
receiver не https или если список бизнесов пуст. В выводе она печатает **id проекта** — именно
его вы подтверждаете в разделе Sources.

## 8. Что осталось за вами

Три пункта, каждый — из-за конкретного ограничения доступа, а не из-за неготовности.

1. **Recovery gate.** Копия есть, восстановление не проверено. Выберите: (а) принять
   snapshot-only и разрешить миграции с явно открытым gate; (б) разрешить одноразовый
   сервис Postgres как цель восстановления, чтобы проверить восстановление и потом удалить
   его; (в) проверить восстановление самостоятельно позже, а миграции пока не применять.
   Без вашего ответа миграции не применяю.

2. **Секрет моста.** Новый секрет нужен только локальному producer; старый в рамках GE-5 не
   отзывается, O9 остаётся открытым. Шаг, который могу сделать только не я: в Railway →
   проект `selena-os-staging` → сервис `receiver` → Variables добавить в
   `SELENA_AETHER_BRIDGE_SECRET` **новое значение первым, через запятую, сохранив старое**
   (например `<новый>,<старый>`), сгенерировав новое значение кнопкой генератора. Затем
   скопировать новое значение в локальный `backend/.env`. В чат его присылать не нужно и не
   надо: я его не читаю и не проверяю. Причина, по которой это не делаю я: чтобы составить
   список, нужно прочитать действующий production-секрет, а он не должен попадать в сессию.

3. **Порядок миграций.** Issue #29 открыт; выбранный порядок не требует от второй ветки
   никаких действий, и защита в раннере теперь не даст тихо потерять миграцию ни одной из
   сторон. Нужно ваше слово: ждать ответа второго исполнителя или считать согласование
   достаточным и продолжать.

Путь к вкладке резервных копий, если понадобится: Railway → проект `selena-os-staging` →
сервис `Postgres` → вкладка `Backups` (том `selena-os-staging-pgdata`).

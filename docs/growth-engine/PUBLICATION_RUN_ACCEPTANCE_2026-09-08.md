# Приёмка прогона до первой публикации

Документ ведётся по ходу ТЗ «довести Selena Systems до первой настоящей
публикации». Каждый этап закрывается доказательством того же типа, что и в
предыдущей программе: id деплоев, строки логов, счётчики внешних эффектов,
прогоны тестов на настоящей базе. Незакрытое названо незакрытым.

## Этап 1 — командный доступ

**Что доказано.** Правило «после первого аккаунта пускает только выписанное
приглашение» проверено на настоящей базе, на слитом `main` (`59e4281a`):
`packages/lib/src/db/invited-signup.integration.test.ts`, 8 из 8, одноразовая
база под миграциями с нуля. Проверены все способы, которыми приглашение
перестаёт действовать: потрачено, отозвано, просрочено, адрес не тот.

**Чего нет.** Приёмки на самом стенде staging — синтетическими аккаунтами через
штатную форму входа. Сессия работает через шлюз исходящего трафика, которому
разрешены только `backboard.railway.com` и `backend.blotato.com`; ни
`staging-cabinet.selenasystems.com`, ни домен боевого контура из неё не
открываются (`CONNECT tunnel failed, 403`). Законного обхода нет: подделывать
сессию владельца нельзя, а её аккаунт занят единственным местом в local-режиме.
Остаётся за владельцем — выписать приглашение в кабинете и открыть ссылку.

**Развёрнуто.** `main` @ `a5cc5355` на staging web, деплой `16b30828`, SUCCESS,
16:16 UTC 07.09. PR #40 влит.

## Этап 7 — цепочка собрана

`apps/worker/src/selena-release-dispatch.ts` и точка `POST /v1/release-dispatches`
в шлюзе; `selena-release-gateway-client.ts` и выбор транспорта у диспетчера —
теперь одобренный выпуск действительно доходит до шлюза, а не останавливается в
очереди навсегда. Миграция `0044` даёт терминальную запись о переносе, `0045` —
владельческую форму привязки канала. PR parkourcafe/selena-os#48 влит в `main`
(`54ddd184`), все семь проверок зелёные, включая pgTAP с новым набором.
Резервирование и авторизация коммитятся до обращения к провайдеру, исход пишется
второй транзакцией: падение на полпути оставляет `RESERVED`, а не теряет след
отправки, которая могла уйти. Отказ политики публикации записывается как
`NOT_SENT` — попытка, которая никуда не ушла.

Доказательства: `apps/worker` 49 проходящих тестов (из них 10 на клиент шлюза и
переносчик, 5 на отправку); полный прогон pgTAP — 418 утверждений, 0 отказов;
все 46 миграций применяются с нуля на одноразовой базе.

## Чего эта сессия не может сделать в принципе

Исходящий трафик ограничен двумя хостами, поэтому ни один кабинет и ни один
публичный адрес из неё не открывается. Всё, что доказывается только через
браузер или HTTP к продукту, остаётся за владельцем либо за сессией с другим
доступом. Это ограничение среды, а не признак того, что код не работает.

## Этап 7 — цепочка выкачена на боевой контур

**Дефект, который нашёл первый настроенный контур.** Воркер боевого контура
падал при старте: `Web runtime context must represent an interactive session`.

## Выбор бренда в кабинете

Найдено по вопросу владельца на боевом кабинете: переключения между брендами в
интерфейсе не существовало вовсе — бренд появляется только в адресе, и ссылки на
создание бренда тоже нигде не было. Хуже, чем «нет»: не определено. Вход в
Content OS брал первую строку неупорядоченного запроса, поэтому организация с
двумя брендами могла в разные заходы открывать разные очереди одобрения.

Порядок задан (старший первым, id как разрыв ничьей), правило «какой бренд
открывается» вынесено в одну функцию с тестами: запомненный выбор побеждает,
пока бренд на месте, иначе старший. Вход показывает список брендов, когда их
больше одного, меню продукта возвращает к этому выбору, создание бренда
доступно из интерфейса. PR parkourcafe/selena-os#51, семь проверок зелёные,
влит в `main` (`29f7ac9a`).

Замечание для заведения бренда: id получается из имени, а `/app/selena` — адрес
страницы выбора рабочего пространства. Поэтому бренд называется **Selena
Systems** (`selena-systems`), а не «Selena».

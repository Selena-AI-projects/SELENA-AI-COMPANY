## Дополнение: две точечные правки перед живым запуском

### Проверка фактов: структура отделена от смысла

`checkOutput` в `writer.mjs` проверяет только структуру: существование `evidence_id`, числа, адреса, запрещённые фразы, отсутствие новых id и чисел в английской версии. Соответствие смысла утверждения источнику она не проверяет и теперь так и называется. Изменения:

- `verification.md` начинается двумя раздельными статусами: «Структурные проверки: пройдены / НЕ пройдены · Смысловая сверка с источником: не выполнена», с абзацем о том, чего автоматика не делает. Раздел «Смысловая сверка (вручную, весь текст)» со статусом «не выполнена» и порядком ручной сверки RU, EN и Telegram с фрагментами `page.txt`.
- `manifest.json` → `checks: { structural: {ok, errors, warnings}, semantic: { status: "pending-manual", scope: [три файла], checkedAt: null, … } }`. Комментарий в первой строке `article.*.md` несёт оба статуса.
- Слова, расширяющие охват («по всему миру», «worldwide», «во всех странах» и т. п.), которых нет в доказательствах, попадают в предупреждения как подсказка редактору — не как вердикт.
- Проверочный пример в тестах (8-й тест): источник — «testing the Gemini-powered assistant … with a small group of restaurants and hotels in the United States»; текст — «уже доступен ресторанам и отелям по всему миру» под тем же `q1`. Структурная проверка проходит (`structural.ok: true` — это и есть предел автоматики), пакет получает `semantic.status: "pending-manual"`, в `verification.md` нет «Статус: пройдена», есть предупреждение «widens scope». Статуса «факты проверены» такой материал не получает — его не получает ни один свежий пакет.

Ранее собранный пакет на тестовых данных (`_test-data/…`, версии `d6a30df4af10` → `e44c4b534f10`) создан до этого разделения: его `verification.md` ещё содержит старую строку «Статус: пройдена». Ручная сверка с `page.txt` записана выше только для русской статьи **первой** версии (`d6a30df4af10`); для второй версии, для английской адаптации и для анонса построчная сверка текста с `page.txt` не делалась — они проверены только структурно (id, числа, автоматическая сверка id с русской версией). Сверенным этот пакет не считается; он и не предназначен к публикации.

### Бюджет и разрешения

Было: обе попытки `claude -p` получали полный `--max-budget-usd`, а метаданные второй попытки затирали стоимость первой. Стало (`run.mjs`):

- оценки всех попыток суммируются: `writer.attempts[]` (каждая со своей оценкой и выданным бюджетом), `attemptCount`, `estimatedCostUsd`, `remainingBudgetUsd`, `budgetUsd`;
- повтор получает только остаток `budgetUsd − оценка первой попытки`; при остатке ≤ 0 или неизвестной оценке повтор не выполняется, в отказе записано `budgetStop`;
- поле `costUsd` переименовано в `estimatedCostUsd`, рядом `costBasis`: «оценка CLI, не фактическое списание и не гарантированный денежный потолок»;
- перед модельным вызовом `checkAuth()` читает `claude auth status`: нужен `loggedIn: true`, `authMethod: oauth_token`, `apiProvider: firstParty` и отсутствие `ANTHROPIC_API_KEY` в окружении; иначе отказ `refused:auth` без вызова модели; результат проверки сохраняется в `writer.auth`.

Тесты без реальных вызовов модели (9-й и 10-й): скриптовый писатель с заданными оценками — первая попытка 0,30 при бюджете 1 не проходит проверку, вторая получает ровно 0,70, сумма 0,55, остаток 0,45, обе попытки в метаданных; при бюджете 0,25 и оценке первой попытки 0,30 — одна попытка, отказ с `budgetStop`; при неизвестной оценке — одна попытка; при `ANTHROPIC_API_KEY` в окружении или не-подписочном входе — модель не вызывается ни разу. ## Дополнение: правки по итогам состязательного ревью

Независимое ревью правок (три линзы: арифметика бюджета и авторизация; тесты против ТЗ; честность формулировок; каждое замечание проверял отдельный скептик) подтвердило восемь замечаний, одно отклонило. Исправлено:

- **Ошибка вызова модели теряла все метаданные.** `runClaude` бросал исключение на `is_error` до сборки метаданных, `main` его не ловил — при остановке CLI по бюджету на повторе (`error_max_budget_usd`) ни `refusal.json`, ни строки в `runs.jsonl`, ни оценки первой попытки не оставалось. Теперь оценка едет на ошибке (`error.meta`), каждый вызов обёрнут, при сбое записывается отказ «вызов модели завершился ошибкой» с `writerMeta` по всем попыткам и строка `refused:writer-error`. Тест 11: первая попытка 0,30 не проходит проверку, вторая падает с оценкой 0,26 — в `refusal.json` две попытки, сумма 0,56.
- **Повтор при остатке меньше одного вызова.** CLI останавливается только после ответа, пересёкшего лимит, поэтому остаток меньше оценки первой попытки лимитом не был бы. Повтор при таком остатке не выполняется (`budgetStop`: «остаток … меньше оценки первой попытки»). Тест: бюджет 0,50, первая попытка 0,30 → один вызов.
- **`claude auth status` при выходе из аккаунта** завершается кодом 1, но печатает JSON; раньше это записывалось как «unreadable» с `loggedIn: null`. Теперь JSON читается и из ошибки, причина — `loggedIn=false`; «unreadable» только когда JSON нет. Тест воспроизводит выход с кодом 1.
- **Пустая проверка в тесте 8**: регулярное выражение с `\b` после кириллицы не могло совпасть ни с чем, то есть не проверяло отсутствие «факты проверены». Заменено на проверку, которая может упасть (регистронезависимо, после удаления единственного разрешённого предложения-отрицания), плюс точная строка заголовка статуса.
- **Заголовочный комментарий `writer.mjs`** обещал, что «предложение без опоры в источниках не попадёт в черновик» — это то самое утверждение о достоверности, которое запрещено ТЗ и которое опровергает тест 8. Переписан: только структурные проверки, смысл читает редактор.
- **Сетевая инструкция**: названы оба имени уровня (Custom по документации сайта, Limited по встроенной справке), указано, что редактировать нужно окружение сессии («Default»).
- **Строка о тестовом пакете** в этом файле завышала сделанное: ручная сверка была только для русской статьи первой версии; английская адаптация и анонс проверялись структурно. Исправлено выше.
- README: авторизация проверяется один раз на запуск, не «перед каждым вызовом»; задокументирован `--max-verify`; описан отказ при ошибке вызова.

Отклонено ревью: предложение требовать поле `subscriptionType` в `auth status` — в контейнере вход идёт через файл токена, для которого CLI это поле не выдаёт; такая проверка отказывала бы именно той среде, где идёт живой запуск. Оставлено: `loggedIn`, `authMethod: oauth_token`, `apiProvider: firstParty`, без `ANTHROPIC_API_KEY`. Замечание ревью на будущее: на машине с обычным `claude /login` CLI может выдавать `authMethod: claude.ai` — тогда проверка откажет (без расходов), и правило нужно будет расширить осознанно, а не ослабить.
